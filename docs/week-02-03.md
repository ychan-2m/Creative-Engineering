# 2~3주차 — WebTalk 기획 및 프로토타입 구현

## 진행 내용

브라우저 기반 1대1 메신저를 프로젝트 주제로 정하고, 회원가입 → 로그인 → 상대 검색 → 방 생성 → 실시간 대화 → 기록 조회 흐름을 코드로 구성했습니다.
이 기록은 2~3주차 작업을 묶어 정리한 것으로, 개별 기능의 정확한 개발 날짜를 구분하지 않습니다.

## 무엇을 어떻게 구현했는지

| 구현 내용 | 구현 방식 | 관련 코드 |
| --- | --- | --- |
| 회원가입 | 입력값과 중복 아이디를 검사하고 BCrypt로 비밀번호 해시 저장 | `auth/`, `user/` |
| 로그인·로그아웃 | Spring Security 인증 결과를 HTTP 세션에 저장, 로그아웃 시 무효화 | `auth/` |
| 사용자 검색 | 아이디·닉네임 검색 결과에서 본인을 제외 | `user/` |
| 1대1 방 | 기존 방이 있으면 반환하고 없으면 방과 두 구성원을 생성 | `chat/` |
| 실시간 메시지 | `/app/chat.send`로 받아 저장 후 `/topic/chat/{roomId}` 구독자에게 발행 | `websocket/`, `message/` |
| 대화 기록 | 방 구성원 여부 확인 후 최근 50개 메시지를 시간순으로 반환 | `message/` |
| 전송 상태 | `clientMessageId`로 전송 중 말풍선과 서버 응답을 연결, 시간 초과 시 재시도 제공 | `static/js/chat.js` |
| 연결 관리 | 연결 상태 표시와 최대 5회 재연결 시도 | `static/js/socket.js` |
| 화면 | 순수 HTML/CSS/JavaScript로 가입·로그인·채팅 화면 구성 | `static/` |
| 데이터 저장 | 사용자·방·구성원·메시지를 H2 파일 DB에 저장 | `schema.sql`, `application.yml` |

Java 패키지 경로는 `webtalk/src/main/java/com/example/webtalk/`,
화면과 설정 경로는 `webtalk/src/main/resources/` 기준입니다.

## 핵심 처리 흐름

1. 로그인 시 만든 세션으로 API 요청과 WebSocket 연결의 사용자를 식별합니다.
2. 방을 선택하면 메시지 토픽을 구독하고 REST API로 기록을 불러옵니다.
3. 서버가 메시지 발신자의 방 참여 여부와 내용 길이를 검사합니다.
4. 메시지 저장 트랜잭션이 끝난 뒤 방 토픽으로 응답을 전달합니다.
5. 화면에서 응답의 요청 ID를 사용해 전송 상태를 갱신합니다.

## 검증 결과

- `./mvnw test`: 성공. 컨텍스트 로딩 테스트 1개, 실패 0개, 오류 0개.
- 테스트 DB는 인메모리 H2를 사용합니다.
- 이 결과는 애플리케이션 컨텍스트 로딩 확인이며, 실시간 송수신 전체의 검증 결과는 아닙니다.
- 브라우저 두 계정 시연 및 권한·재시도 기능의 수동 확인 결과는 추후 기록합니다.

## 현재 한계와 다음 작업

- 읽음 처리 API가 없어 안 읽은 수 배지가 정확한 읽음 상태를 반영하지 않습니다.
- 현재 선택한 방만 구독하며 다른 방의 실시간 알림은 없습니다.
- 재연결 후 누락 메시지 조회와 동시 중복 요청 처리를 보완해야 합니다.
- 최근 50개 이전 대화의 추가 조회 UI, 파일 전송, 단체 채팅은 구현하지 않았습니다.
- 다음 단계는 기능 검증, 읽음 처리 개선, 실행 화면 기록입니다.
